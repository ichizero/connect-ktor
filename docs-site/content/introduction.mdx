# Introduction

Connect-Kotlin already gives JVM and Android clients a typed Connect client.
Connect-Ktor answers the other half of that sentence: a Ktor server that can accept those calls without abandoning the REST routes already in production.

## The gap it fills

Connect has strong client libraries and a clear protocol story.
On the JVM server side, many teams still run Ktor with handwritten JSON REST.

Rewriting that surface as gRPC is often the wrong trade.
gRPC wants HTTP/2 end-to-end, a different tooling culture, and a sharper break from browser-friendly APIs.

Connect sits closer to ordinary HTTP.
Unary calls look like POST (or GET when idempotent).
JSON and binary Protobuf both work.
That is why it fits an existing Ktor app: you add handlers, you do not replace the transport stack.

## Relationship to Connect-Kotlin

Connect-Ktor reuses Connect-Kotlin types and serialization strategies on the server.
Handlers return `ResponseMessage`, throw `ConnectException`, and speak the same error model clients already expect.

Code generation is split on purpose:

- `protoc-gen-connect-kotlin` (official) produces clients
- `protoc-gen-connect-ktor` (this project) produces Ktor route handler interfaces

Both read the same `.proto` services.
A React app on Connect-ES and a Ktor service on Connect-Ktor can share one Buf module without inventing a parallel schema.

## Who it is for

- Teams with a Ktor REST API who want Protobuf RPCs for new or hot paths
- Stacks that already pair **React (Connect-ES)** with **Kotlin/Ktor**
- Services that need Connect conformance for unary and client-streaming today, and can wait on server/bidi streaming

It is a poor fit if you need gRPC wire compatibility or full-duplex streams on day one.
Those limits are documented under [Known limitations](/known-limitations), not hidden behind a feature checklist.

## Design stance

Prefer coexistence over conversion.
A single `embeddedServer` can expose `/api/v1/...` REST routes and `/package.Service/Method` Connect procedures at once.

Prefer protocol honesty over completeness theater.
Unsupported axes stay ❌ in the matrix until the implementation and the conformance pins agree.
